TMDL and Model-Driven Development: Generate vs. Hand-Craft

2026-03-07 · 11 min read

Why the future of semantic model development is generation, not authoring

---

!TMDL hand-craft versus generate, illustrated as two workflows converging on the same Fabric-hosted semantic model — one built manually with inconsistent measures, the other assembled from consistent, auto-generated TMDL files/tmdl-and-model-driven-development-generate-vs-handcraft/assets/01_hero/01_hero.png)

TMDL (Tabular Model Definition Language) changed everything for Power BI developers. For the first time, semantic models have a human-readable, Git-friendly, text-based format that can be versioned, diffed, and reviewed like code.

But here's the question nobody's asking: should you write TMDL by hand?

The answer, increasingly, is no. TMDL is a good target format and a bad source format. The moment it becomes something you hand-author, you've recreated the exact problem it was supposed to fix — just in a nicer syntax.

This article makes the case for treating TMDL as a build artifact, the same way you'd treat compiled code or a generated SQL script: never edited directly, always regenerated from something upstream that actually deserves to be the source of truth.

---

What TMDL Solved — and What It Didn't

TMDL replaced the binary .bim format and verbose JSON of TMSL with a clean, readable syntax:


table Sales
    lineageTag: 8f2c7b9d-1234-5678-90ab-cdef12345678

    column Amount
        dataType: decimal
        formatString: \$#,0.00
        summarizeBy: sum
        sourceColumn: Amount

    column ProductID
        dataType: int64
        isHidden: true
        sourceColumn: ProductID

    measure 'Total Revenue' = SUM(Sales[Amount])
        formatString: \$#,0.00
        description: "Sum of all sales amounts"

    measure 'Revenue YTD' =
        CALCULATE(
            [Total Revenue],
            DATESYTD('Date'[Date])
        )
        formatString: \$#,0.00
        description: "Year-to-date revenue"

What TMDL genuinely fixed:

  • Human-readable (unlike binary .bim)
  • Git-friendly (real diffs, not JSON noise)
  • Modular (one file per table)
  • IDE-compatible (syntax highlighting, IntelliSense)

What it didn't fix is where the definitions come from. TMDL gave semantic models a better serialization format. It didn't give them a source of truth. Teams adopted it, opened Tabular Editor or VS Code, and kept doing exactly what they did before — typing measure definitions by hand — just in a format that's easier to diff. The format upgraded; the workflow didn't.

---

The Hand-Crafting Problem

Most teams adopt TMDL and immediately start writing it by hand. This seems natural — it's text, after all, and text feels like source.

But hand-crafting TMDL creates the same four problems every hand-crafted artifact creates once more than one person touches it.

Problem 1: Inconsistency

Different developers write different styles:


-- Developer A
measure 'Total Sales' = SUM(Sales[Amount])

-- Developer B
measure TotalSales = SUM ( Sales[Amount] )

-- Developer C
measure 'total_sales' = sum(Sales[Amount])

Same logic, three styles. Which is correct? Without a standard, they all are — and now your semantic layer has three naming conventions living side by side.

Problem 2: Documentation Drift

Descriptions start strong, then decay:


-- Week 1: Well documented
measure 'Total Revenue' = SUM(Sales[Amount])
    description: "Sum of all sales amounts after discounts, excluding returns"

-- Week 10: Description outdated
measure 'Total Revenue' = SUM(Sales[NetAmount])  -- Changed column
    description: "Sum of all sales amounts after discounts, excluding returns"
    -- Description still says "Amount", code uses "NetAmount"

Nobody updates a comment as a separate step. The code changes; the sentence next to it doesn't.

Problem 3: Duplication

Time intelligence measures get copy-pasted across models:


-- Model A: Sales
measure 'Revenue YTD' = CALCULATE([Total Revenue], DATESYTD('Date'[Date]))

-- Model B: Marketing (copy-pasted, slightly modified)
measure 'Spend YTD' = CALCULATE([Total Spend], DATESYTD('Date'[Date]))

-- Model C: Operations (copy-pasted, bug introduced)
measure 'Cost YTD' = CALCULATE([Total Cost], DATESYTD('Calendar'[Date]))
    -- Oops: Different date table name

Copy-paste is how a correct pattern quietly becomes three slightly-wrong ones.

Problem 4: No Single Source of Truth

The semantic model becomes the definition. But what defined the semantic model? Requirements in a Word doc? A conversation in Slack? A memory of what someone said in standup three weeks ago? Nobody knows — and nobody can regenerate the model from anything but the model itself.

These aren't TMDL's failures. They're what happens whenever the thing you hand-write is also the thing you'd need to govern. TMDL didn't cause this; it just makes it more visible, because now the drift shows up as a Git diff instead of disappearing into a binary blob.

---

The Model-Driven Alternative

Structure beats magic here in the most literal sense: the fix isn't a smarter way to write TMDL, it's refusing to write it at all. Model-driven development inverts the workflow so structure — explicit, versioned metadata — does the work that used to depend on one developer's discipline and memory.


Traditional:
  Requirements → [Human brain] → TMDL → Semantic Model

Model-Driven:
  Requirements → YAML Metadata → [Generator] → TMDL → Semantic Model

The metadata is the source of truth. TMDL is a generated artifact — you read it, you diff it in a PR, you never type it.

MDDE YAML as Source


# entities/sales.yaml
entities:
  - name: Sales
    stereotype: dim_fact
    description: "Customer sales transactions"

    attributes:
      - name: Amount
        type: decimal(18,2)
        description: "Transaction amount after discounts"
        format: currency

      - name: ProductID
        type: int
        description: "Reference to product dimension"
        hidden: true

    measures:
      - name: Total Revenue
        expression: SUM([Amount])
        description: "Sum of all sales amounts"
        format: currency
        time_intelligence:
          - YTD
          - PY
          - YoY

Generated TMDL


/// This file is auto-generated from MDDE metadata.
/// Source: entities/sales.yaml
/// Generated: 2026-03-07T14:30:00Z
/// Do not edit manually.

table Sales
    lineageTag: auto-generated-uuid

    column Amount
        dataType: decimal
        formatString: \$#,0.00
        summarizeBy: sum
        sourceColumn: Amount
        description: "Transaction amount after discounts"

    column ProductID
        dataType: int64
        isHidden: true
        sourceColumn: ProductID
        description: "Reference to product dimension"

    measure 'Total Revenue' = SUM(Sales[Amount])
        formatString: \$#,0.00
        description: "Sum of all sales amounts"

    measure 'Total Revenue YTD' =
        CALCULATE(
            [Total Revenue],
            DATESYTD('Date'[Date])
        )
        formatString: \$#,0.00
        description: "Year-to-date: Sum of all sales amounts"

    measure 'Total Revenue PY' =
        CALCULATE(
            [Total Revenue],
            SAMEPERIODLASTYEAR('Date'[Date])
        )
        formatString: \$#,0.00
        description: "Prior year: Sum of all sales amounts"

    measure 'Total Revenue YoY' =
        VAR CurrentValue = [Total Revenue]
        VAR PriorValue = [Total Revenue PY]
        RETURN DIVIDE(CurrentValue - PriorValue, PriorValue)
        formatString: 0.0%
        description: "Year-over-year change: Sum of all sales amounts"

What just happened:

1. One measure definition → four generated measures

2. Consistent naming: [Base] YTD, [Base] PY, [Base] YoY

3. Descriptions auto-prefixed with time context

4. Format strings appropriate to measure type

This is metadata as code: the YAML is what gets reviewed, tested, and merged. TMDL is what comes out the other end — never the other way around.

---

Why Generation Wins

1. Consistency by Default

The generator enforces style. Every measure follows the same pattern.


# Generator configuration
naming:
  measures:
    ytd_suffix: " YTD"
    py_suffix: " PY"
    yoy_suffix: " YoY"
  columns:
    case: PascalCase

No debate, no drift. Style is configuration, not discipline — which means it survives a team change, a deadline crunch, or a new hire who never read the naming-convention doc.

2. Documentation Is Automatic

Descriptions come from metadata. When metadata changes, descriptions regenerate — this is living documentation: it evolves with the platform because it's derived, not typed alongside it.


# Change once in YAML
attributes:
  - name: Amount
    description: "Net transaction amount after discounts and returns"

Regenerate → all references updated. There's no second place to remember to update.

3. Time Intelligence Is Free

Define once in metadata, generate all variants:


measures:
  - name: Revenue
    expression: SUM([Amount])
    time_intelligence:
      - YTD
      - QTD
      - MTD
      - PY
      - PQ
      - PM
      - YoY
      - QoQ
      - MoM

That's 10 measures from one definition. Each is correctly named, formatted, and documented — none of it copy-pasted, so none of it can silently diverge.

4. Multi-Target Generation

The same YAML generates multiple outputs:


# Single source
entities:
  - name: Sales
    attributes:
      - name: Amount
        type: decimal(18,2)

Generate:

  • SQL DDL: CREATE TABLE sales (amount DECIMAL(18,2))
  • dbt model: {{ config(materialized='table') }} SELECT amount FROM ...
  • TMDL: column Amount dataType: decimal
  • Documentation: Markdown with column definitions

One truth, many representations. This is the same move that made model-driven data engineering work for SQL and dbt in the first place — TMDL is just the newest target it can point at.

5. Validation Before Generation

Errors caught at metadata level, not after deployment:


METADATA VALIDATION
===================
Error: Entity "Sales" has measure "Revenue" referencing
       non-existent attribute "Ammount" (typo?)

Suggestion: Did you mean "Amount"?

Catching a typo in a YAML validator costs a red line in CI. Catching the same typo after deployment costs a support ticket, a Teams thread, and someone's afternoon.

---

The Workflow

Step 1: Define Metadata


# entities/sales.yaml
entities:
  - name: Sales
    stereotype: dim_fact
    description: "Customer sales transactions"
    source:
      schema: raw
      table: fact_orders
    attributes:
      - name: OrderDate
        type: date
        description: "Date order was placed"
        role: date_key
      - name: Amount
        type: decimal(18,2)
        description: "Net transaction amount"
    measures:
      - name: Total Revenue
        expression: SUM([Amount])
        time_intelligence: [YTD, PY, YoY]

Step 2: Validate


mdde validate entities/

Output:


Validating entities/sales.yaml...
  ✓ Entity "Sales" has valid stereotype
  ✓ All attributes have descriptions
  ✓ Measure expressions are valid DAX
  ✓ Time intelligence references valid date role

All validations passed.

Step 3: Generate TMDL


mdde export powerbi --format tmdl --output ./tmdl/

Output:


Generating TMDL from 12 entities...
  → Sales.tmdl (4 columns, 7 measures)
  → Customer.tmdl (8 columns, 0 measures)
  → Product.tmdl (6 columns, 0 measures)
  → Date.tmdl (12 columns, 0 measures)
  → relationships.tmdl (6 relationships)
  → model.tmdl (model-level properties)

Generated 6 TMDL files.

Step 4: Deploy


mdde fabric deploy --workspace "Sales Analytics" --model ./tmdl/

Handling Edge Cases

"But what about complex measures that don't fit templates?"

Custom DAX in Metadata


measures:
  - name: Rolling 12 Month Average
    expression: |
      VAR Last12Months =
          DATESINPERIOD(
              'Date'[Date],
              MAX('Date'[Date]),
              -12,
              MONTH
          )
      RETURN
          AVERAGEX(
              Last12Months,
              CALCULATE([Total Revenue])
          )
    description: "Average monthly revenue over trailing 12 months"

The generator passes through custom DAX verbatim. You get the best of both worlds: templated measures where patterns apply, custom DAX where they don't.

Calculation Groups


calculation_groups:
  - name: Time Intelligence
    items:
      - name: Current
        expression: SELECTEDMEASURE()
      - name: YTD
        expression: CALCULATE(SELECTEDMEASURE(), DATESYTD('Date'[Date]))
      - name: PY
        expression: CALCULATE(SELECTEDMEASURE(), SAMEPERIODLASTYEAR('Date'[Date]))

Generated as proper TMDL calculation group syntax.

---

When to Hand-Craft

There are legitimate cases for manual TMDL:

1. Prototyping — quick experiments before committing to metadata

2. One-off fixes — emergency production patches

3. Legacy migration — importing existing models before converting to metadata

But even then, the goal is metadata-first. Hand-crafted TMDL should be temporary — a scratchpad on the way to a YAML definition, not a permanent home.

---

CI/CD Integration

The model-driven approach integrates naturally with CI/CD — this is semantic DevOps: meaning ships on a release train, not by hand.


# .github/workflows/semantic-model.yml
name: Semantic Model CI/CD

on:
  push:
    paths:
      - 'entities/**/*.yaml'
      - 'measures/**/*.yaml'

jobs:
  validate-and-deploy:
    steps:
      - name: Validate Metadata
        run: mdde validate ./entities/

      - name: Generate TMDL
        run: mdde export powerbi --format tmdl --output ./tmdl/

      - name: Run Best Practice Analyzer
        run: npx @pbi-tools/bpa ./tmdl/

      - name: Deploy to Development
        run: mdde fabric deploy --workspace "Dev" --model ./tmdl/

The key insight: YAML changes trigger the pipeline. TMDL is never committed to Git — it's a build artifact, exactly like a compiled binary or a generated SQL script.

---

Comparison: Hand-Craft vs. Generate

| Aspect | Hand-Craft | Generate |

|--------|------------|----------|

| Consistency | Depends on discipline | Enforced by generator |

| Documentation | Manual, drifts | Automatic, always current |

| Time intelligence | Copy-paste per measure | Define once, generate all |

| Multi-target | Separate files | Single source |

| Validation | After deployment | Before generation |

| Code review | Review TMDL (verbose) | Review YAML (concise) |

| Refactoring | Find/replace risk | Regenerate safely |

| Onboarding | Learn TMDL syntax | Learn YAML schema |

---

Getting Started

For New Projects

Start with metadata. Define your entities in YAML, generate TMDL from day one.


# Initialize MDDE project
mdde init --template powerbi

# Define first entity
mdde entity create Sales --stereotype dim_fact

# Generate TMDL
mdde export powerbi --format tmdl

For Existing Projects

Import existing TMDL into metadata, then switch to generation:


# Import existing model
mdde import powerbi --source ./existing-model.bim --output ./entities/

# Review and enhance imported metadata
code ./entities/

# Regenerate (verify round-trip)
mdde export powerbi --format tmdl --output ./new-tmdl/

# Compare
diff -r ./existing-model/ ./new-tmdl/

---

Key Takeaways

1. TMDL is an output, not an input — treat it like compiled code, not source.

2. Metadata is the source of truth — YAML definitions drive everything.

3. Generation enforces consistency — no style debates, no documentation drift.

4. Time intelligence is multiplicative — one measure definition, many variants.

5. Multi-target generation — same metadata produces SQL, dbt, TMDL, docs.

6. Validation shifts left — catch errors in metadata, not after deployment.

7. CI/CD is natural — YAML changes trigger pipelines, TMDL is never committed.

The question isn't whether to use TMDL. TMDL is a good format either way. The question is whether it's the thing you write or the thing your pipeline writes for you — and once you've seen the second version work, going back to typing measures by hand feels like editing a compiled binary.
