MDDE Adoption Framework: Minimal Metadata for Your Use Case

2025-10-15 · 11 min read

Don't deploy the whole platform. Deploy exactly what you need.

---

Most metadata platforms suffer from feature bloat. You adopt one capability and inherit two hundred database tables you'll never query. The MDDE Adoption Framework maps modules to metadata, so you deploy only what your use case requires — and can show, table by table, why each one is there.

!MDDE Adoption Framework hero image: a towering pile of paperwork labelled core, governance, operations shrinking down to two clean stacked entities — core and lineage — next to icons for docs, lineage and quality/mdde-adoption-framework-minimal-metadata-for-your-use-case/assets/01_hero/01_hero.png)

---

The metadata bloat problem

You want to implement data lineage. Just lineage.

You install a metadata platform and discover it created:

  • 47 tables for "core metadata"
  • 23 tables for "governance"
  • 15 tables for "operations"
  • 12 tables for "collaboration"
  • …

97 tables for lineage? You needed maybe five.

This is metadata bloat, and it isn't an accident — it's the default outcome when nobody mapped the dependencies. Platforms ship everything because they can't articulate which metadata supports which capability, so every table becomes "required" by default. That's magic dressed up as completeness: impressive on a diagram, unaccountable in a review. Structure beats magic means the opposite discipline — every table earns its place by a traceable dependency, or it doesn't ship.

---

The module-metadata matrix

The MDDE Adoption Framework introduces a clear mapping: every module declares its metadata dependencies. Not "the platform needs 380 entities" — "this specific capability needs these specific entities, and here's why."


┌─────────────────────────────────────────────────────────────────────────────┐
│                         MODULE-METADATA MATRIX                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  MODULE                    REQUIRED ENTITIES          CHILD MODELS          │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  yaml_models               model, entity, attribute   core                  │
│  sql_generation             model, entity, attribute   core                  │
│                                                                             │
│  entity_lineage             entity, entity_mapping     core, lineage         │
│  column_lineage             attribute, attr_mapping,   core, lineage         │
│                              entity_mapping                                  │
│                                                                             │
│  quality_checks             entity, attribute,         core, governance      │
│                              simple_check                                    │
│                                                                             │
│  data_vault                 model, entity, attribute,  core, reference       │
│                              stereotype                                      │
│                                                                             │
│  unity_catalog               model, entity, attribute,  core, integration     │
│                              layer                                           │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

If you only need lineage, you deploy core + lineage child models — perhaps 15 entities instead of 380+.

If you only need documentation, you deploy core — maybe 5 entities.

This is metadata as code: the dependency between a module and its entities isn't tribal knowledge in someone's head, it's a declared, version-controlled mapping you can query, diff and review like any other artefact.

The Adoption Advisor

The AdoptionAdvisor class generates personalized recommendations based on your profile — this is where the module-metadata matrix becomes a planning tool, not just documentation.


from mdde.planning.adoption_framework import (
    AdoptionAdvisor,
    AdoptionProfile,
    LifecycleStage,
    ResourceLevel,
    UseCase,
)

# Define your context
profile = AdoptionProfile(
    name="Regional Bank Risk Platform",
    industry="banking",
    lifecycle_stage=LifecycleStage.DEVELOPMENT,
    resource_level=ResourceLevel.MODERATE,  # 3-5 people
    use_cases=[UseCase.MIGRATION, UseCase.LINEAGE, UseCase.QUALITY],
    regulations=["BCBS_239", "GDPR"],
)

# Get recommendations
advisor = AdoptionAdvisor()
subset = advisor.recommend(profile)

print(f"Modules recommended: {len(subset.modules)}")
print(f"Setup days: {subset.total_setup_days}")
print(f"Learning hours: {subset.total_learning_hours}")
print(f"Metadata entities needed: {len(subset.required_entities)}")

Output:


Modules recommended: 12
Setup days: 18.5
Learning hours: 52
Metadata entities needed: 28

The advisor:

1. Finds matching modules — based on your use cases and regulations

2. Resolves dependencies — if you need column_lineage, you automatically get entity_lineage

3. Filters by constraints — if you're at "minimal" resource level, enterprise-grade features are excluded

4. Prioritizes — "must have" vs "recommended" vs "optional"

5. Calculates metadata — exactly which entities you need to deploy

The advisor's day/hour estimates aren't guesses — they come from the same catalog, so a scoping conversation with a client can point at a number instead of a feeling.

Entity annotations

Every metadata entity can be annotated with its module relevance:


from mdde.planning.adoption_framework import get_entity_annotation

annotation = get_entity_annotation("entity")
print(annotation)

Output:


EntityAnnotation(
    entity_name='entity',
    child_model='core',
    modules=['yaml_models', 'sql_generation', 'model_validation',
             'discovery', 'ai_documentation', 'entity_lineage',
             'column_lineage', 'impact_analysis', 'quality_checks', ...],
    use_cases=['documentation', 'modeling', 'migration', 'governance',
               'quality', 'lineage', 'devops', 'ai_enablement'],
    is_core=True  # Used by 5+ modules
)

This enables:

  • Schema annotations — document which modules use which entities
  • Documentation — auto-generate module-entity relationship docs
  • Governance — understand impact of schema changes

Minimal deployment example

Here's how to deploy only what you need.

Step 1: Generate your minimal subset


# For documentation + quality
result = get_minimal_entity_set([UseCase.DOCUMENTATION, UseCase.QUALITY])

print(f"Deploy these child models: {result['child_models_needed']}")
print(f"Total entities: {result['total_entities']}")

Step 2: Export required schema


# Generate DDL for only the required child models
mdde schema export \
  --child-models core governance \
  --output minimal_schema.sql

Step 3: Validate your deployment


# Verify all required entities exist
mdde validate deployment \
  --required-entities model,entity,attribute,simple_check

IP sharing: only share what's relevant

The Adoption Framework also enables selective IP sharing.

When working with customers, you don't need to share the entire MDDE codebase. You can identify exactly which modules are relevant to their use case:


# Customer needs migration + lineage
modules_for_customer = advisor.get_use_case_modules(UseCase.MIGRATION)
modules_for_customer += advisor.get_use_case_modules(UseCase.LINEAGE)

# Generate module list for sharing
for module in modules_for_customer:
    print(f"- {module.display_name}: {module.description}")

This clarity enables:

  • Scoped licensing — license only the modules customers use
  • Focused training — train only on relevant capabilities
  • Lighter deployments — fewer entities = faster setup

This is the tool-extender model in one mechanism: MDDE isn't a framework a client adopts wholesale, it's a set of accelerators scoped to exactly the modules their use case needs, layered onto tools they already run (dbt, Databricks, their own DDL). Nothing gets shared, licensed or taught beyond what the engagement actually touches.

The bidirectional map

The framework maintains a bidirectional mapping:

Entity → Modules


from mdde.planning.adoption_framework import get_entity_modules

# Which modules use the 'entity_mapping' entity?
modules = get_entity_modules("entity_mapping")
# → ['entity_lineage', 'column_lineage', 'impact_analysis', 'lineage_diagrams']

Module → Entities


from mdde.planning.adoption_framework import get_module_entities

# Which entities does 'column_lineage' require?
entities = get_module_entities("column_lineage")
# → ['attribute', 'attribute_mapping', 'entity_mapping',
#    'function_param_mapping', 'entity_window_param_mapping']

This bidirectionality enables impact analysis — if you modify an entity, you know which modules are affected.

Why this matters

For platform implementers

  • Deploy faster — no unnecessary tables
  • Reduce complexity — fewer moving parts
  • Lower costs — less storage, compute, maintenance

For consultants

  • Scope clearly — know exactly what a project requires
  • Estimate accurately — setup days and learning hours are documented
  • Avoid over-engineering — don't deploy features that won't be used

For customers

  • Start small — adopt incrementally
  • Understand dependencies — know what's required before you start
  • Grow when needed — add modules as use cases expand

---

Summary

The MDDE Adoption Framework answers the question every platform adopter asks:

"What do I actually need to deploy?"

Instead of shipping 380+ entities "just in case", the framework:

1. Maps modules to metadata — every module declares its dependencies

2. Maps use cases to modules — documentation needs different modules than regulatory compliance

3. Calculates minimal subsets — exactly which entities for your use case

4. Generates roadmaps — phased implementation with effort estimates

5. Enables selective sharing — share only what's relevant to each customer

None of this requires you to adopt a platform. It requires a metadata operating system — a declared, queryable map of what depends on what — layered onto the tools you already run. That's the whole thesis: structure beats magic, applied to your own deployment.

Stop deploying everything. Deploy what you need.
