Sidecar Tables: Companion Metadata for Data Assets

2026-03-05 · 14 min read

How auxiliary tables let metadata travel with your data without polluting the business schema

Introduction

Every data engineer has met this table: customer — clean, twelve business columns, and then created_at, updated_at, created_by, quality_score, last_checked_at, version_number, previous_value bolted on because nobody had a better place to put them. Give it a year and the "clean business entity" is half operational plumbing. Your ETL now populates a dozen extra columns nobody downstream asked for, and every consumer scrolls past metadata to find the three fields they actually need.

Sidecar tables fix this the same way good structure always does: by separating concerns instead of hoping discipline holds. The main table stays business data. Companion tables — sidecars — carry the operational metadata: history, quality, audit, load statistics, configuration. Same subject, different lifecycle, different table.

This is [[concept-structure-beats-magic|Structure Beats Magic]] applied to schema design. There's no clever trick here — just a naming convention and a decision about where metadata lives, applied consistently until the pattern becomes invisible infrastructure.

What is a Sidecar Table?

A sidecar table is a companion table that:

1. References the main table via foreign key

2. Tracks metadata that doesn't belong in the main entity

3. Has its own lifecycle — it can be truncated, archived, or dropped independently of the business data it describes

4. Follows naming conventions that make the relationship obvious from the table name alone

The term borrows from the sidecar pattern in microservices architecture, where a helper container runs alongside the main application container handling cross-cutting concerns — logging, monitoring, security — without the application itself needing to know. Same idea, applied to tables instead of containers: the main table doesn't need to know its sidecars exist.

Sidecar Table Categories

1. Version Tables (_version)

Track the complete history of an entity using SCD Type 2 semantics.

Purpose: Answer "What did this record look like at time X?"

Structure:


entity_version:
  attributes:
    - version_id: VARCHAR (PK)
    - entity_id: VARCHAR (FK to main table)
    - version_sequence: INTEGER
    - valid_from: TIMESTAMP
    - valid_to: TIMESTAMP
    - is_current: BOOLEAN
    - changed_by: VARCHAR
    - change_reason: VARCHAR
    # ... snapshot of all versioned attributes

Example:


-- Main table
CREATE TABLE customer (
    customer_id VARCHAR PRIMARY KEY,
    name VARCHAR,
    email VARCHAR,
    segment VARCHAR
);

-- Version sidecar
CREATE TABLE customer_version (
    version_id VARCHAR PRIMARY KEY,
    customer_id VARCHAR REFERENCES customer(customer_id),
    version_sequence INTEGER,
    name VARCHAR,
    email VARCHAR,
    segment VARCHAR,
    valid_from TIMESTAMP,
    valid_to TIMESTAMP,
    is_current BOOLEAN,
    changed_by VARCHAR
);

When to use:

* Regulatory requirements for audit trails

* Time-travel queries

* Debugging data issues

If this smells like SCD2, it is — the pattern behind [[concept-pit-helper-tables|PIT helper tables]] in the MDDE temporal layer. A _version sidecar is where that history physically lives before anything pre-joins it for fast as-of queries.

2. History Tables (_history)

Track specific changes to attributes or status transitions.

Purpose: Answer "What changed, when, and why?"

Structure:


entity_status_history:
  attributes:
    - history_id: VARCHAR (PK)
    - entity_id: VARCHAR (FK)
    - status_dimension: VARCHAR  # Which status changed
    - old_value: VARCHAR
    - new_value: VARCHAR
    - changed_at: TIMESTAMP
    - changed_by: VARCHAR
    - change_reason: VARCHAR

Example:


-- Track status transitions for orders
CREATE TABLE order_status_history (
    history_id VARCHAR PRIMARY KEY,
    order_id VARCHAR REFERENCES order(order_id),
    old_status VARCHAR,
    new_status VARCHAR,
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    changed_by VARCHAR,
    change_reason VARCHAR
);

Difference from _version:

* _version: full row snapshots, answers "what was the complete state?"

* _history: change events, answers "what specifically changed?"

3. Quality Tables (_quality, _quality_sidecar)

Store data quality metrics and attestations.

Purpose: Answer "How trustworthy is this data?"

Structure:


entity_quality_sidecar:
  attributes:
    - batch_id: VARCHAR (PK)
    - attestation_id: VARCHAR
    - load_timestamp: TIMESTAMP
    - row_count: INTEGER
    - overall_status: VARCHAR      # PASSED, WARNING, FAILED
    - overall_score: DECIMAL
    - completeness_score: DECIMAL
    - uniqueness_score: DECIMAL
    - validity_score: DECIMAL
    - passed_checks: INTEGER
    - failed_checks: INTEGER
    - attestation_json: JSON       # Full attestation detail

Example:


-- Quality sidecar for transactions
CREATE TABLE fct_transactions_quality_sidecar (
    batch_id VARCHAR PRIMARY KEY,
    load_timestamp TIMESTAMP,
    row_count INTEGER,
    overall_status VARCHAR,
    overall_score DECIMAL(5,4),
    completeness_score DECIMAL(5,4),
    uniqueness_score DECIMAL(5,4),
    total_checks INTEGER,
    passed_checks INTEGER,
    attestation_json JSON
);

-- Query: "Should I trust today's data?"
SELECT batch_id, overall_status, overall_score
FROM fct_transactions_quality_sidecar
WHERE load_timestamp >= CURRENT_DATE
  AND overall_status = 'PASSED';

This is the pattern the companion article on quality metadata exchange covers in depth: the quality sidecar is how trust travels with data instead of living in someone's dashboard, disconnected from the rows it describes.

4. Log Tables (_log)

Track operational events: loads, deployments, executions.

Purpose: Answer "What happened during processing?"

Structure:


entity_load_history:
  attributes:
    - load_id: VARCHAR (PK)
    - entity_id: VARCHAR (FK)
    - batch_id: VARCHAR
    - load_start: TIMESTAMP
    - load_end: TIMESTAMP
    - rows_inserted: INTEGER
    - rows_updated: INTEGER
    - rows_deleted: INTEGER
    - status: VARCHAR              # SUCCESS, FAILED, PARTIAL
    - error_message: VARCHAR

Example:


-- Deployment log for models
CREATE TABLE model_deployment_log (
    deployment_id VARCHAR PRIMARY KEY,
    model_id VARCHAR,
    version_tag VARCHAR,
    environment VARCHAR,
    deployed_at TIMESTAMP,
    deployed_by VARCHAR,
    deployment_ticket VARCHAR,
    status VARCHAR
);

5. Audit Tables (_audit)

Track who accessed or modified data and when.

Purpose: Answer "Who did what and when?" — compliance and security territory.

Structure:


entity_audit:
  attributes:
    - audit_id: VARCHAR (PK)
    - entity_id: VARCHAR (FK)
    - action: VARCHAR              # SELECT, INSERT, UPDATE, DELETE
    - performed_by: VARCHAR
    - performed_at: TIMESTAMP
    - client_ip: VARCHAR
    - session_id: VARCHAR
    - affected_rows: INTEGER

6. Configuration Tables (_config, _def)

Store runtime parameters and definitions.

Purpose: Answer "How should this entity behave?"

Structure:


entity_config:
  attributes:
    - config_id: VARCHAR (PK)
    - entity_id: VARCHAR (FK)
    - config_key: VARCHAR
    - config_value: VARCHAR
    - effective_from: TIMESTAMP
    - effective_to: TIMESTAMP

Example:


-- PIT generation configuration
CREATE TABLE dim_customer_pit_config (
    config_id VARCHAR PRIMARY KEY,
    entity_id VARCHAR,
    pit_generation_enabled BOOLEAN,
    snapshot_frequency VARCHAR,
    retention_days INTEGER
);

* dim_product → dim_product_status_history, dim_product_quality_sidecar

Implementation Patterns

Pattern 1: Foreign Key Reference

The simplest pattern — sidecar references main table:


CREATE TABLE customer_version (
    version_id VARCHAR PRIMARY KEY,
    customer_id VARCHAR NOT NULL REFERENCES customer(customer_id),
    -- versioned attributes...
);

Pros: strong referential integrity. Cons: cannot create a sidecar record before the main record exists.

Pattern 2: Loose Coupling

Sidecar stores the reference without an FK constraint:


CREATE TABLE customer_quality_sidecar (
    batch_id VARCHAR PRIMARY KEY,
    entity_name VARCHAR NOT NULL,  -- 'customer'
    -- quality metrics...
);

Pros: sidecar can exist independently, works for external data. Cons: no referential integrity guarantee.

Pattern 3: Composite Key Reference

For sidecars that track attributes rather than whole entities:


CREATE TABLE attribute_propagation_history (
    history_id VARCHAR PRIMARY KEY,
    entity_id VARCHAR NOT NULL,
    attribute_id VARCHAR NOT NULL,
    -- history details...
    FOREIGN KEY (entity_id, attribute_id)
        REFERENCES attribute(entity_id, attribute_id)
);

Pattern 4: JSON Sidecar Column

Sometimes a full sidecar table is overkill. Embed as JSON instead:


CREATE TABLE fct_transactions (
    transaction_id VARCHAR PRIMARY KEY,
    amount DECIMAL(18,2),
    -- business columns...
    -- Embedded sidecar as JSON
    _quality_attestation JSON,
    _lineage_metadata JSON
);

Pros: no join needed, data travels together. Cons: harder to query, index, and maintain.

When to Use Sidecar Tables

Use Sidecars When:

1. Separation of concerns — operational metadata shouldn't pollute business data

2. Different lifecycles — you want to archive or purge sidecars independently

3. Different access patterns — consumers rarely need the metadata

4. Compliance requirements — audit trails must be immutable

5. Multiple metadata types — one main table needs version + quality + audit, and cramming all three into one wide table would be worse than three focused ones

Avoid Sidecars When:

1. Simple audit columns suffice — created_at, updated_at cover your needs

2. Performance is critical — every join adds latency

3. Metadata is always needed — if consumers always need quality scores, embed them

4. Volume is low — the overhead isn't justified for small tables

This is the honest trade-off, not a rule to apply everywhere. A sidecar you always have to join is a normalization decision you're paying for on every query — sometimes a wide table with a few extra columns is the right call, and the discipline is knowing which situation you're in.

Quality Sidecar in Detail

The quality sidecar pattern deserves a closer look because it's the one that enables an actual data trust decision — not just a record of what happened, but a gate a consumer can query before deciding whether to use the data at all:


-- Producer creates quality attestation
INSERT INTO fct_transactions_quality_sidecar (
    batch_id,
    load_timestamp,
    row_count,
    overall_status,
    overall_score,
    completeness_score,
    uniqueness_score,
    attestation_json
) VALUES (
    'batch_20260301_001',
    '2026-03-01 10:00:00',
    1500000,
    'PASSED',
    0.9875,
    0.9950,
    1.0000,
    '{"checks": [...], "environment": "PROD", "producer_version": "v2.1.0"}'
);

-- Consumer queries quality before using data
SELECT t.*, q.overall_status, q.overall_score
FROM fct_transactions t
JOIN fct_transactions_quality_sidecar q ON t.batch_id = q.batch_id
WHERE q.overall_status = 'PASSED'
  AND q.overall_score >= 0.95;

Quality travels with data. Consumers can make informed decisions about data trustworthiness without a side conversation with the producer team — the attestation sits right next to the rows it describes, queryable the same way. That's [[concept-metadata-as-code|metadata as code]] in practice: not a wiki page claiming the data is good, a table you can join against.

Best Practices

1. Consistent Naming

Follow the {main_entity}_{sidecar_type} pattern religiously:


✅ customer_version
✅ customer_status_history
✅ customer_quality_sidecar

❌ customer_hist           # Unclear abbreviation
❌ version_customer        # Wrong order
❌ tbl_customer_versions   # Hungarian notation

2. Common Columns

Include standard columns in all sidecars:


# Origin tracking
origin_id: VARCHAR      # Source of this record
origin_type: VARCHAR    # yaml_import, sql_parser, api, etc.

# Audit tracking
created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

3. Indexing Strategy

Index the foreign key and the common query patterns:


-- Always index the FK
CREATE INDEX idx_customer_version_customer_id
    ON customer_version(customer_id);

-- Index temporal queries
CREATE INDEX idx_customer_version_valid_from
    ON customer_version(valid_from);

-- Index current record lookup
CREATE INDEX idx_customer_version_current
    ON customer_version(customer_id, is_current)
    WHERE is_current = TRUE;

4. Retention Policies

Define retention independently for each sidecar — this is exactly the "different lifecycle" argument made concrete:


retention_policies:
  customer:
    retention: forever          # Business data kept indefinitely
  customer_version:
    retention: 7_years          # Regulatory requirement
  customer_quality_sidecar:
    retention: 90_days          # Operational data, shorter retention
  customer_load_history:
    retention: 30_days          # Debug data, shortest retention

5. Documentation

Document the relationship in metadata, not tribal knowledge:


# customer.yaml
entity:
  name: customer
  sidecars:
    - type: version
      table: customer_version
      purpose: SCD2 history for regulatory compliance
    - type: quality
      table: customer_quality_sidecar
      purpose: DQ attestation per load batch
    - type: history
      table: customer_status_history
      purpose: Segment transition audit

Querying Sidecars

Point-in-Time Query (Version Sidecar)


-- What was customer 123's segment on Jan 1, 2026?
SELECT cv.segment
FROM customer_version cv
WHERE cv.customer_id = '123'
  AND cv.valid_from <= '2026-01-01'
  AND (cv.valid_to > '2026-01-01' OR cv.valid_to IS NULL);

Change History Query (History Sidecar)


-- Show all segment changes for customer 123
SELECT
    old_value AS previous_segment,
    new_value AS new_segment,
    changed_at,
    change_reason
FROM customer_status_history
WHERE entity_id = '123'
  AND status_dimension = 'segment'
ORDER BY changed_at;

Quality-Gated Query (Quality Sidecar)


-- Only use data from batches that passed quality
SELECT t.*
FROM fct_transactions t
JOIN fct_transactions_quality_sidecar q
    ON t.batch_id = q.batch_id
WHERE q.overall_status = 'PASSED'
  AND q.completeness_score >= 0.99;

Load Statistics Query (Log Sidecar)


-- Recent load performance
SELECT
    load_start,
    load_end,
    load_end - load_start AS duration,
    rows_inserted,
    rows_updated,
    status
FROM customer_load_history
WHERE load_start >= CURRENT_DATE - INTERVAL '7 days'
ORDER BY load_start DESC;

Conclusion

Sidecar tables aren't a clever trick — they're a naming convention and a placement decision, applied with enough discipline that the pattern becomes invisible. That's the whole point, and it's why it belongs under Structure Beats Magic: there's no AI, no framework, no magic step. Just a rule — metadata about data lives beside the data, not inside it — applied consistently across every entity in the model.

Follow it and you get:

1. Clean business tables — only business data in business tables

2. Time-travel — full historical audit trails, queryable without archaeology

3. Trust that travels — quality attestations sit next to the rows they describe

4. Debuggability — load logs and operational metrics at your fingertips

5. Compliance you can prove — immutable audit trails for regulatory requirements

The pattern generalizes beyond any one tool: [[concept-metadata-mesh|metadata mesh]] thinking says each domain owns and publishes its metadata as a product. Sidecar tables are the physical implementation of that idea at the table level — the metadata product lives right beside the data it describes, not in a separate catalog you have to trust is still in sync. Metadata about data is also data. It deserves its own schema design, not a dozen columns tacked onto the end of a CREATE TABLE statement because nobody made the call.
