Atomic SQL: Self-Contained Data Pipelines That Carry Their Own Metadata

2026-03-02 · 13 min read

A SQL file that documents itself is a SQL file that can't drift from its own documentation

The problem: metadata sprawl

In most data platforms, metadata doesn't live in one place — it lives in five:

  • ETL tools hold pipeline schedules and dependencies
  • Data catalogs hold descriptions and classifications
  • Governance platforms hold PII tags and ownership
  • Quality tools hold validation rules
  • BI tools hold metric definitions

Call it what it is: metadata sprawl. The same column gets described five times, in five tools, by people who never talk to each other — and the descriptions inevitably contradict. This is innocent SQL one level up: nobody lies about what a column means, everybody just documents it slightly differently, and the drift compounds until nobody trusts any single answer.

!Diagram showing the metadata sprawl problem: a single table sitting between Airflow, Unity Catalog, dbt, Purview, a data-quality tool and Looker, each holding a different fragment of the table's metadata, with the question "which source is correct?"/atomic-sql-self-contained-data-pipelines-that-carry-their-own-metadata/assets/01_hero/01_hero.png)

Ask a new team member "what does this column mean?" and you get six different answers — one per tool, and none of them the SQL that actually produced the value.

The fix: Atomic SQL

Atomic SQL is a design pattern where every SQL file is self-contained: pipeline, transformation, and column metadata all live as structured comments inside the file itself. The query runs with zero external metadata dependencies — no catalog lookup, no orchestrator config, no separate quality-rule store required to execute it. But at deployment time, that same metadata is extracted and published outward to whatever platforms need it: the orchestrator, the catalog, the quality tool.

Think of it as a shipping container for a data transformation: the container carries the manifest of what's inside, so nobody downstream has to guess.

The anatomy of an Atomic SQL file


-- ============================================================================
-- HEADER: Pipeline Identity
-- ============================================================================
-- @pipeline: customer_360_daily
-- @version: 2.1.0
-- @owner: data-platform@company.com
-- @schedule: 0 6 * * *
-- @target: gold.dim_customer
-- @stereotype: dim_scd2
-- @depends_on: silver.clean_customers, silver.fact_orders
-- ============================================================================

WITH
-- ============================================================================
-- CTE: What this transformation step does
-- @cte: deduplicated
-- @grain: one row per customer_id
-- @description: Remove duplicates, keep most recent record
-- ============================================================================
deduplicated AS (
    SELECT *,
        ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) as rn
    FROM silver.clean_customers
)
-- ============================================================================
-- OUTPUT: Target table with quality expectations
-- @output: gold.dim_customer
-- @pk: customer_key
-- @check: not_null(customer_id, email)
-- @check: unique(customer_id)
-- ============================================================================
SELECT
    customer_id,                    -- @nk: natural key
    email,                          -- @tag: pii, gdpr
    lifetime_value                  -- @tag: metric, currency_usd
FROM deduplicated
WHERE rn = 1;

One file, four things it can do without leaving Git:

1. Execute immediately in any SQL environment — no metadata store required.

2. Be reviewed with full context in a PR — the metadata change sits next to the code change.

3. Be deployed with automatic metadata extraction into orchestrator, catalog, quality tool.

4. Be versioned with complete history — git blame tells you who tagged a column PII, and when.

Why "atomic"?

In chemistry, an atom is the smallest unit that still retains the properties of an element — split it further and you lose what made it that element. An Atomic SQL file works the same way: it's the smallest deployable unit that still retains every property of the pipeline. Split the metadata out into a separate catalog entry, and you've reintroduced the drift the pattern exists to kill.

!Comparison table: for each property (transformation logic, dependencies, schedule, quality checks, column metadata, ownership), Atomic SQL keeps it "in the file" while the traditional approach scatters it across Airflow, dbt, orchestrator, quality tool, catalog and governance tool/atomic-sql-self-contained-data-pipelines-that-carry-their-own-metadata/assets/03_figure/03_figure.png)

That table is the whole argument in one glance: in the traditional approach, only the transformation logic reliably lives in the file. Everything else is a pointer to some other tool's opinion.

The three zones of annotation

Atomic SQL uses three annotation zones, each scoped to a different level of the pipeline.

Zone 1: header (pipeline-level)

The header block carries metadata about the entire pipeline:


-- ============================================================================
-- @pipeline: customer_360_daily
-- @version: 2.1.0
-- @owner: data-platform@company.com
-- @schedule: 0 6 * * *
-- @target: gold.dim_customer
-- @stereotype: dim_scd2
-- @depends_on: silver.clean_customers, silver.fact_orders
-- @sla: freshness=6h, quality=99.5%
-- @certified: true
-- @description: |
--   Builds unified customer dimension from CRM and order data.
--   Implements SCD Type 2 for historical tracking.
--   Critical for customer analytics dashboards.
-- ============================================================================

Extractable to:

  • Airflow / Databricks Workflows — schedule, dependencies
  • Data catalog — owner, description, certification
  • Monitoring — SLA expectations

Zone 2: CTE comments (transformation-level)

Each CTE gets its own comment block explaining what it does and why:


-- ============================================================================
-- @cte: order_enrichment
-- @description: Calculate customer lifetime metrics from order history
-- @grain: one row per customer_id
-- @joins: silver.fact_orders ON customer_id
-- @aggregation: SUM(order_total), COUNT(order_id)
-- @business_rule: Only include orders with status = 'completed'
-- ============================================================================
order_enrichment AS (
    SELECT
        customer_id,
        SUM(order_total) as lifetime_value,
        COUNT(order_id) as total_orders
    FROM silver.fact_orders
    WHERE status = 'completed'
    GROUP BY customer_id
)

Why this matters:

  • Future maintainers understand the transformation logic without archaeology
  • Lineage tools can infer column-level relationships from the annotations, not just the joins
  • AI assistants can explain what each step does — the explanation is in the file they're reading

Zone 3: column annotations (inline)

Column-level metadata sits right next to the column definition, not three tools away:


SELECT
    customer_id,                          -- @nk: natural key from CRM
    email,                                -- @tag: pii, gdpr, mask_on_export
    CONCAT(first_name, ' ', last_name)    -- @derived: concatenation
        as full_name,
    segment,                              -- @enum: enterprise, smb, consumer
    lifetime_value,                       -- @tag: metric, currency_usd
                                           -- @aggregation: sum
    health_score                          -- @tag: metric, derived
                                           -- @range: 0-100
                                           -- @business_context: enterprise_model
FROM enriched

Why inline?

  • Metadata is visible during code review, not hidden behind a separate PR to a separate repo
  • Column and metadata change together, in the same diff, or not at all
  • No drift between what the code does and what the documentation claims it does

The deployment pipeline

Atomic SQL files don't need a metadata store to execute — but at deployment time, the metadata gets extracted and pushed out to every platform that needs a copy:

Nothing here is exotic — it's a parser reading structured comments and a set of API calls to the tools you already run. That's the point: Atomic SQL doesn't replace Airflow, Unity Catalog, or your quality platform. It's the metadata as code layer that keeps them all fed from one source instead of five independently-maintained ones.

Handling complex transformations

Real pipelines aren't one CTE. Here's how the pattern scales.

Multi-CTE pipelines


-- @pipeline: customer_360_daily
-- @target: gold.dim_customer

WITH
-- @cte: raw_dedupe | @grain: 1 row/customer_id
raw_dedupe AS (
    SELECT *, ROW_NUMBER() OVER (...) as rn
    FROM silver.clean_customers
),
-- @cte: order_metrics | @grain: 1 row/customer_id | @joins: fact_orders
order_metrics AS (
    SELECT customer_id, SUM(total) as ltv, COUNT(*) as orders
    FROM silver.fact_orders
    GROUP BY customer_id
),
-- @cte: segment_rules | @business_rule: RFM segmentation
segment_rules AS (
    SELECT
        customer_id,
        CASE
            WHEN ltv > 10000 AND orders > 10 THEN 'vip'
            WHEN ltv > 5000 THEN 'high_value'
            WHEN orders > 5 THEN 'frequent'
            ELSE 'standard'
        END as segment
    FROM order_metrics
),
-- @cte: final_join | Combines all CTEs
final AS (
    SELECT r.*, o.ltv, o.orders, s.segment
    FROM raw_dedupe r
    JOIN order_metrics o ON r.customer_id = o.customer_id
    JOIN segment_rules s ON r.customer_id = s.customer_id
    WHERE r.rn = 1
)
-- @output: gold.dim_customer
SELECT * FROM final;

Incremental loads


-- @pipeline: orders_incremental
-- @target: silver.fact_orders
-- @mode: incremental
-- @watermark: order_date
-- @lookback: 3 days

-- @cte: new_orders | Fetch only new/updated records
WITH new_orders AS (
    SELECT *
    FROM bronze.raw_orders
    WHERE order_date >= '{{ watermark }}' - INTERVAL '3 days'
)
-- @output: silver.fact_orders
-- @merge_key: order_id
-- @update_columns: status, updated_at
SELECT * FROM new_orders;

Parameterized queries


-- @pipeline: monthly_aggregation
-- @target: gold.monthly_metrics
-- @parameters:
--   - name: year_month
--     type: string
--     format: YYYY-MM
--     default: {{ current_month }}

WITH monthly AS (
    SELECT
        DATE_TRUNC('month', order_date) as month,
        SUM(total) as revenue
    FROM silver.fact_orders
    WHERE DATE_TRUNC('month', order_date) = '{{ year_month }}-01'
    GROUP BY 1
)
SELECT * FROM monthly;

Quality checks in Atomic SQL

Quality expectations live in the same file as the transformation they guard:


-- ============================================================================
-- QUALITY CHECKS
-- @check: not_null(customer_id, email)
-- @check: unique(customer_id)
-- @check: unique(customer_id, valid_from)  -- SCD2 uniqueness
-- @check: range(health_score, 0, 100)
-- @check: enum(segment, 'enterprise', 'smb', 'consumer', 'startup')
-- @check: referential(customer_id, silver.clean_customers.customer_id)
-- @check: freshness(updated_at, 24h)
-- @check: row_count(min=1000, max=10000000)
-- @check: custom("lifetime_value >= 0 OR status = 'inactive'")
-- ============================================================================

At deployment, these get:

1. Scheduled to run right after the pipeline

2. Registered in the data quality platform

3. Monitored, with alerts wired to failures

The benefits

1. Portability

Move the file, and everything moves with it — nothing to recreate on the other side:


# Copy from dev to prod
cp pipelines/customer_360.sql /prod/pipelines/

# Deploy - metadata travels with the file
mdde deploy /prod/pipelines/customer_360.sql --env prod

No re-recreating DAGs. No re-tagging columns. No re-entering quality rules by hand in a second tool.

2. Code review = metadata review

Change a column from VARCHAR to DECIMAL, and the PR shows both changes in one diff:


SELECT
-     lifetime_value,                 -- @tag: metric, varchar
+     CAST(lifetime_value AS DECIMAL) -- @tag: metric, currency_usd
+         as lifetime_value,          -- @precision: 15,2

The reviewer sees the code change and the metadata change together, because they are the same change.

3. No drift

The traditional failure mode:


Code says:     email VARCHAR(255)
Catalog says:  email VARCHAR(100)
Quality says:  email NOT NULL
Governance:    email is PII (maybe?)

Four tools, four half-true answers. Atomic SQL collapses it to one:


email VARCHAR(255)    -- @tag: pii, gdpr | @check: not_null

One source. No drift. Ever — because there's nowhere else for a second answer to live.

4. Git-native history


$ git log --oneline pipelines/customer_360.sql

a1b2c3d Add health_score metric
d4e5f6g Mark email as GDPR-sensitive
g7h8i9j Change SLA from 12h to 6h
j0k1l2m Add referential integrity check
m3n4o5p Initial pipeline creation

Every metadata change is tracked with author, timestamp, and commit message — the same audit trail you already trust for code, now covering governance decisions too.

5. AI-ready

When an assistant needs to explain your data, the explanation is already sitting in the file it's reading:


User: "What does the health_score column mean?"

AI: Looking at customer_360.sql...
The health_score column:
- Is a derived metric (tagged: metric, derived)
- Ranges from 0-100 (check: range)
- Uses enterprise_model business context
- Is calculated in the 'scored' CTE using RFM formula:
  - Recency: 40% weight
  - Frequency: 30% weight
  - Monetary: 30% weight

This is the part worth naming plainly: structure beats magic here too. The AI isn't guessing from a vague prompt or hallucinating a plausible-sounding answer — it's reading structure that a human deliberately put in place. Good output stops being luck and becomes repeatable the moment the metadata is actually there to read.

Implementation checklist

Ready to adopt Atomic SQL? Four phases, roughly in order.

Phase 1 — Annotation standard

  • Define annotation syntax (@tag, @check, etc.)
  • Document which annotations go where — header, CTE, column
  • Create linting rules to validate annotations
  • Build an annotation reference for your team

Phase 2 — Parser

  • Build a SQL parser that extracts annotations
  • Handle multi-line values (descriptions)
  • Support all annotation types
  • Unit test extensively — this is the piece everything else depends on

Phase 3 — Deployment integration

  • Connect to your orchestrator (Airflow, Databricks, etc.)
  • Connect to your catalog (Unity, Purview, etc.)
  • Connect to your quality platform (dbt, Great Expectations, etc.)
  • Build the deploy command that ties them together

Phase 4 — Migration

  • Inventory existing pipelines
  • Generate annotations from existing metadata sources — don't hand-type what you can extract
  • Review and enhance the generated annotations
  • Deprecate the external metadata sources once the SQL file is the trusted copy

Conclusion

Atomic SQL isn't a new language, and it isn't a framework you adopt wholesale. It's a design pattern that treats a SQL file as a complete, self-documenting package — and you can apply it inside dbt, SQLMesh, plain Airflow, or any orchestrator's deployment step. Extend whatever you already run; don't rip it out.

The principles are simple:

1. Metadata belongs with code — not scattered across five separate tools

2. One source of truth — the SQL file, not a catalog entry that might be stale

3. Extract, don't duplicate — publish outward to platforms from the file, never the reverse

4. Version everything — a metadata change is a code change, reviewed the same way

The result is pipelines that are:

  • Portable — move anywhere, metadata follows
  • Auditable — Git history captures every governance decision, not just every code change
  • Reviewable — PRs show the full context, not just the diff
  • Trustworthy — no drift between what the code does and what the catalog claims it does

Start with one pipeline. Add the annotations. Extract to your platforms. Scale from there — the fifth pipeline is cheaper than the first, because the parser and the deploy step are already built.
