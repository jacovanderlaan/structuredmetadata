Rulebooks Playbooks And Cookbooks

The book family: rulebooks enforce, playbooks direct, cookbooks show, runbooks execute — each a structured document of text plus metadata, built from segments.

The book family. Four kinds of structured document, distinguished by what they do to the reader — enforce, direct, show, or execute. Naming them separately matters because organisations collapse them into one undifferentiated "documentation", and then wonder why none of it gets used.

| Book | Answers | Binding? | Reader | |---|---|---|---| | Rulebook | *What must always be true* | Enforced automatically | The platform (and the auditor) | | Playbook | *How we handle this situation* | Procedural, judgment allowed | A person deciding | | Cookbook | *How this is built, in practice* | Pattern, freely adapted | A builder, mid-task | | Runbook | *What to do, step by step, now* | Deterministic, no judgment | Whoever is on duty — or an agent |

The distinction is not formality but what happens when you deviate. Break a rulebook and the pipeline fails. Deviate from a playbook and you explain yourself. Ignore a cookbook and you have written something bespoke. Skip a runbook step and the thing does not work.

Text plus metadata

A book in this family is never prose alone. Each is a hybrid: readable text for the human, structured metadata for the machine — owner, scope, version, applicability, the systems it governs, when it was last validated. The metadata is what makes a book *findable, checkable and executable*; the text is what makes it understandable.

That is the difference between a book and a document. A document is read. A book is queried — "which rulebooks apply to this domain", "which runbooks haven't been exercised this quarter", "which playbook covers this incident type" — and it can be checked for staleness without anyone opening it.

Built from segments

Books have structure below the document level: segments, each individually addressable. A rulebook is a set of rules, not a wall of text about rules. A runbook is a sequence of steps. A cookbook is a collection of patterns.

Segments are what make the family useful rather than decorative:

- Reuse — the same segment appears in several books without being copied. One definition, many contexts. - Provenance — a segment can point at the decision, interview or model element it came from. - Precision — you cite *this step*, not "somewhere in the deployment doc". - Generation — a segment can be produced from the model, so parts of a book are never hand-written. - Validation — a step marked executed, a rule marked enforced, a pattern marked deprecated. Individually.

A document that cannot be addressed below its own title is a document. A book made of segments is a structure that happens to read as prose.

Why this is a BTM concept

Books are where methodology stops being a slide and becomes operational. BTM is more than a model — it needs the layer that says how work is actually done, and that layer has to be as structured as the model itself, or it decays into Documentation Theatre.

The test is the same as everywhere else in this library: can this artifact tell you what it is? A book with metadata and segments can. A Word file called `procedures_final_v3.docx` cannot.
